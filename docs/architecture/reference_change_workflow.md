# Reference 對齊與設計修改 workflow

本文件定義從發現差異到結案的流程。`AGENTS.md` 的 protected COM model
規則優先；本流程不授權任何尚未獲批准的核心修改。當前項目與下一個關卡
記在 [`../planning/active_contracts.md`](../planning/active_contracts.md)；
各 TC 的完整證據與決策保留在所連結的契約中。不要用聊天中的「同意繼續」
推定另一份契約已獲批准。

同一時間只設**一個執行焦點**。新發現先登記為 E/G/T 或待辦，除非它阻斷
目前驗收，否則不切換實作。每次回報先說焦點 TC、所在關卡、下一個動作，
再說新發現；完成或明確暫緩目前焦點，才從狀態表選下一項。

## 1. 發現與分類

先固定 case、輸入、候選、相位、grid、單位和比較邊界，逐 stage 找到第一個
不同的中間量。回報順序固定為：**結論／要做什麼 → 目前算法與程式位置 →
spec 或 reference 算法 → 可重現證據 → 修改方案與驗收**。每個 gap 先登記
一個問題 ID，不能只留下 final COM 差值。

| 問題類別 | 判定 | 下一步 |
| --- | --- | --- |
| `E-###` 設計／實作有誤 | 違反適用 spec、已批准契約或數值不變量 | 提出具體修正；涉及 protected kernel 時先取得獨立 Core Model Change Contract 批准 |
| `G-###` design diff | 兩種做法可能均有效，或 reference 使用不同 policy | 逐旋鈕 A/B；決定單一 canonical 做法，或有明確用途的命名 policy |
| `T-###` 待分類 | 證據不足以判定 E/G | 補共同輸入、公式或中間量，不先改模型 |
| 比較條件差異 | case、候選、設定或邊界不一致 | 修正比較方法並重跑；若仍有差異才登記 E/G/T |

`G` 的「分支」指算法 policy 選項，不等於必須建立 Git branch。reference
結果較接近不是改預設的充分理由；只有 spec、物理／數值理由與跨 case
驗證支持時才改 canonical 做法。GUI 選項需另列使用情境與影響。

## 2. 具名契約與批准關卡

每項擬議修改使用唯一編號與具體名稱，例如 `TC-013 — Run-level fixed grid
與 search overflow 補位`。標題不能只寫「修正 COM」。一份契約只處理一個
可獨立驗證、回退的決策；發現新模型問題或超出已批准檔案／函式／公式範圍，
另立契約或修訂版本並重新取得明確批准。設計差異先完成 A/B 與 policy
決策，再提出實作契約；純比較條件修正可以結案而不建程式修改契約。

契約在請求批准**之前**必須列出：

1. ID、名稱、關聯問題 ID、分類、目前狀態與希望使用者決定的事項。
2. 目標及來源：spec 公式／公開 reference／已接受的專案政策；分清強制要求與選項。
3. 目前的算法、資料流和精確程式位置；提議的算法、資料流及可觀察功能。
4. **預計修改檔案與函式清單**，分列 model／utility、search／GUI、測試、文件；各檔案說明改什麼。新增檔案也要列出，禁止籠統寫「相關檔案」。同時列出每項算法的責任層級、呼叫鏈、設定傳遞層與真正執行數值操作的層級；若提議在高層直接改低層結果，須說明理由。
5. 不在範圍內的行為；93A、178A、single run、search run、公開 API／GUI 的影響。
6. 會變及必須不變的中間量；固定 case、預期數值、容差、測試及結案標準。
7. 回退邊界與提交切分；對 protected kernel 滿足 `AGENTS.md` 的十項 Core Model Change Contract 要求。

一般非核心錯誤可在列出範圍後直接修正；protected kernel 的行為和數學文件
只能在該具體契約獲明確批准後編輯。批准只適用該契約明列的範圍。

新契約統一用以下順序，讓使用者先看清要改什麼：

```text
TC-### — 具體名稱
結論與需要的決策：
問題 ID／分類／目前狀態：
預計修改檔案與函式：逐檔列「路徑 → 功能」，另列測試與文件
責任邊界與呼叫鏈：設定在哪裡選、演算法在哪裡執行、哪些層僅轉送
目前算法 → 提議算法：
spec／reference／policy 依據：
不修改的範圍與 93A／178A、single／search 影響：
中間量、固定 case、容差與驗收：
提交切分與回退邊界：
```

若是 Core Model Change Contract，仍須逐項滿足 `AGENTS.md` 的十項要求；
此顯示順序不省略任何一項。

## 3. 實作與驗證關卡

實作前核對 canonical cwd、Git root、`AGENTS.md`、`git status`，並記錄
既有未提交修改；使用專案 `.venv`，測試暫存置於 `%TEMP%` 專用子目錄。
不覆蓋、還原或混入既有修改。先有固定 golden 中間量，再做最小範圍修改；
每次程式變動同步更新所屬 authoritative 文件與必要測試。若實際檔案清單
或公式超出契約，停止該部分並重新提出決策。

驗證依序檢查公式／utility 不變量、固定 case 的第一個差異 stage、後續
中間量與最終結果、93A／178A 回歸，最後才跑 small／full search。
search 的 warning、候選補位、全部候選失敗等執行政策須以測試和實際 run
分別標明；mock 測試不能冒充完整 sweep。記錄命令、環境、輸入、容差、
結果與未驗證的範圍。數值與 reference 接近不取代 spec 公式驗收。

protected model 行為必須使用**獨立 commit**；不得混入 search、reporting、
搬移、格式化等變更。若原檔已有不同來源的未提交修改，先隔離可歸屬的
patch；無法安全隔離時，保留現況並標示「已實作、待隔離提交」，不得把
整檔或既有 index 直接提交，也不得宣稱結案。

## 4. 狀態與結案

每份 TC 只保留一個主狀態，附明確的驗證與提交欄位：

`待分類 → 待決策 → 待批准 → 已批准待實作 → 實作中 → 待驗證 →
待隔離提交 → 已結案`。不需程式修改的診斷可從「待決策」直接結案。
`暫緩`／`受阻` 必須記原因與恢復條件，不能當成已結案。已完成測試但
仍欠實際 sweep 時留在「待驗證」；已通過全部驗收但欠獨立 commit 時為
「待隔離提交」。

每次回報只更新 `active_contracts.md` 的主狀態、下一個關卡與證據連結，
不重複貼所有歷史。只有驗收達標、適用的獨立 commit 存在、authoritative
文件已更新、殘留問題另有 ID 時，才標「已結案」。結案記 commit、測試、
case 與未解的 design diff；之後的 reference 對齊從下一個未結案問題開始。
